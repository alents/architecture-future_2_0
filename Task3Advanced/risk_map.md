# Карта рисков трансформации «Будущее 2.0»

## Контекст

Компания «Будущее 2.0» переходит от монолитного DWH на SQL Server 2008 к доменной архитектуре (Data Mesh) с событийной платформой. Целевой стек: Apache Kafka, Apache Flink, Apache Iceberg, ClickHouse, Starburst/Trino, DataHub, Keycloak. Трансформация рассчитана на 3 года и разбита на три этапа.

## Детальное описание рисков

### Архитектурные риски

#### 1. Деградация производительности Trino при росте числа доменов

Trino — единая точка входа для кросс-доменных запросов и Power BI. Пока доменов пять (деление на домены будет показано в следующем задании), нагрузка терпимая. Но компания планирует подключать фармацевтику, производителя оборудования и выходить в новые регионы. Каждый новый домен — это дополнительные источники, больше данных, больше параллельных запросов. Если не следить за нагрузкой, можно получить ту же проблему медленных отчётов, от которой уходим, только уже на новом стеке.

#### 2. Сложность переходного периода с двумя параллельными архитектурами

Легаси (DWH на SQL Server, ESB Camel, PowerBuilder) и новая архитектура будут жить рядом от полутора до трёх лет. Всё это время нужно поддерживать «мосты совместимости», антикоррупционные слои и следить за тем, чтобы данные в старой и новой системах не расходились. Команды будут параллельно эксплуатировать легаси и осваивать новый стек — это дорого, сложно и утомительно. Но это неизбежная цена поэтапной миграции.

#### 3. Vendor lock-in при выборе облачного провайдера

Сами по себе выбранные технологии (Kafka, Flink, Iceberg, ClickHouse, Trino) — open-source и не привязаны к конкретному облаку. Но на практике при реализации часто выбирают managed-сервисы провайдера: например, Amazon MSK вместо своего Kafka, или AWS Glue как каталог Iceberg. Со временем это накапливается и затрудняет переезд к другому провайдеру. А ведь компания планирует выход в новые регионы, где могут быть требования к локализации данных и потребность в мультиоблачности.

### Организационные риски

#### 4. Нехватка компетенций для нового технологического стека

Сейчас команда работает с SQL Server 2008, PowerBuilder и Apache Camel. А целевой стек — это Kafka, Flink, Iceberg, ClickHouse, Trino, Debezium, DataHub, Keycloak. В Data Mesh каждая доменная команда должна сама вести полный пайплайн от сервиса до витрины. Разрыв между текущими навыками и тем, что нужно — огромный. Без серьёзного обучения, найма или привлечения внешних специалистов трансформация будет буксовать.

#### 5. Сопротивление доменов принятию ответственности за data products

Data Mesh переворачивает привычную модель: раньше за данные отвечал центральный DWH-отдел, а теперь каждый домен должен сам следить за качеством, доступностью и документацией по своим данным. Для доменных команд (клиники, финтех, ИИ) это выглядит как дополнительная работа, не связанная с их основными задачами. Без явной поддержки руководства и понятного распределения ответственности домены будут делать это формально, «для галочки».

#### 6. Платформенная команда как bottleneck для доменов

Центр компетенций Data Mesh — одна команда на всю компанию. Она задаёт стандарты, настраивает общую инфраструктуру (Kafka, Trino, DataHub), консультирует домены, помогает с внедрением. А доменов пять, и у каждого свои приоритеты: финтех торопится из-за регуляторных дедлайнов, клиники хотят стабильности, ИИ-сервисам нужна помощь с потоковой обработкой. Все идут к одной команде. Особенно остро это будет на первом и втором этапах, пока домены ещё не набрали собственную экспертизу. По сути, есть риск заменить старый bottleneck (монолитный DWH-отдел) на новый — перегруженную платформенную команду.

#### 7. Регуляторные риски при миграции медицинских и финансовых данных

Компания работает с данными, которые жёстко регулируются: медицинские данные пациентов и финансовые данные банковских клиентов (есть банковская лицензия). При миграции в новую архитектуру и в облако нужно соблюсти все требования по хранению, обработке, передаче и разграничению доступа. Ошибки здесь — неправильная классификация данных, проблемы с шифрованием, некорректный доступ между доменами — могут привести к штрафам, потере лицензий и репутационному ущербу.

### Технологические риски

#### 8. Сложность одновременного внедрения большого числа технологий

В целевой архитектуре: Kafka, Flink, Iceberg, ClickHouse, Trino, Debezium, DataHub, Keycloak, PostgreSQL. Каждая из этих технологий требует отдельной экспертизы для эксплуатации в проде: настройка кластеров, мониторинг, масштабирование, обновления, разбор инцидентов. Внедрять всё одновременно — значит кратно увеличить количество точек отказа и нагрузку на команду, которая и так осваивает новый стек.

#### 9. Миграция сотен терабайт из SQL Server 2008

В монолитном DWH лежат сотни терабайт исторических данных, которые нужно перенести в доменные Lakehouse (Iceberg). Миграцию нужно провести, не остановив текущие бизнес-процессы. Дополнительная сложность: данные в DWH не разложены по доменам — перед миграцией их нужно декомпозировать и смаппить на доменную модель. Ошибки на этом этапе — потеря данных, неправильная атрибуция, длительный простой аналитики.

#### 10. Обеспечение exactly-once семантики для финансовых данных

Событийный поток в целевой архитектуре: Domain Service → Outbox → Debezium → Kafka → Flink → Iceberg / ClickHouse. На каждом звене при сбоях возможны дубликаты или потери. Для финансового домена (кредиты, платежи, банковская лицензия) это критично: дубль транзакции или потерянный платёж — это прямые финансовые потери и проблемы с регулятором. Нужна тщательная настройка идемпотентности на каждом уровне и серьёзное тестирование.
