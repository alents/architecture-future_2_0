# План управления рисками трансформации «Будущее 2.0»

## Контекст

Документ описывает меры по снижению рисков, выявленных в карте рисков трансформации. Для каждого риска указан тип мер: техническое решение, управленческий подход или комбинация обоих.

---

## Детальные меры по снижению рисков

### Архитектурные риски

#### 1. Деградация производительности Trino при росте числа доменов

**Технические меры:**
- Настроить квоты на ресурсы (CPU, память) для разных категорий запросов, чтобы тяжёлые аналитические запросы не блокировали лёгкие дашбордные.
- Использовать кэширование результатов для часто повторяющихся запросов.
- При необходимости разделить кластеры Trino: один для интерактивных дашбордов, другой для тяжёлой аналитики.

**Управленческие меры:**
- При подключении каждого нового домена проводить оценку нагрузки и при необходимости масштабировать кластер заранее.
- Обучать пользователей писать эффективные запросы, мониторить проблемные запросы.

#### 2. Сложность переходного периода с двумя параллельными архитектурами

**Технические меры:**
- Использовать антикоррупционные слои на границе легаси и новой системы, чтобы изменения в одной не ломали другую.
- Автоматизировать проверки согласованности данных между старой и новой системами.

**Управленческие меры:**
- Зафиксировать принцип: новая бизнес-логика не добавляется в легаси, только в новый стек. Легаси только поддерживается.
- Составить график вывода легаси-компонентов из эксплуатации с конкретными дедлайнами и ответственными за каждый этап.

#### 3. Vendor lock-in при выборе облачного провайдера

**Технические меры:**
- Отдавать предпочтение open-source инструментам (Iceberg вместо проприетарных форматов, Terraform для управления инфраструктурой).
- Избегать глубокой привязки к проприетарным API провайдера там, где есть open-source альтернатива.

**Управленческие меры:**
- Ввести архитектурный принцип: при выборе managed-сервиса облачного провайдера всегда оценивать, насколько сложно и дорого будет от него отказаться.

### Организационные риски

#### 4. Нехватка компетенций для нового технологического стека

**Управленческие меры:**
- Запустить программу обучения по целевому стеку (Kafka, Flink, Iceberg и т.д.) до начала активного внедрения.
- Нанять или привлечь внешних специалистов с опытом работы с целевыми технологиями, как минимум на старте.
- Использовать пилотный домен как площадку для обучения: команда учится на реальном проекте в контролируемых условиях.
- Организовать менторинг от платформенной команды для доменных команд.

#### 5. Сопротивление доменов принятию ответственности за data products

**Управленческие меры:**
- Обеспечить явную поддержку трансформации со стороны руководства компании, чтобы ответственность за данные воспринималась как приоритет, а не как дополнительная нагрузка.
- Включить метрики качества данных (актуальность, полнота, документированность) в показатели эффективности доменных команд.
- Выделить в каждом домене дата-инженера, ответственного за пайплайн и data products домена.

#### 6. Платформенная команда как bottleneck для доменов

**Технические меры:**
- Подготовить типовые шаблоны и пошаговые инструкции для частых задач (вести базу знаний), чтобы доменные команды могли выполнять их самостоятельно.
- Автоматизировать рутинные операции: создание окружений, деплой, мониторинг.

**Управленческие меры:**
- Ввести прозрачную приоритизацию задач платформенной команды: единый бэклог, доступный всем доменам, с понятными критериями приоритета.
- Планировать рост платформенной команды пропорционально количеству подключённых доменов.

#### 7. Регуляторные риски при миграции медицинских и финансовых данных

**Технические меры:**
- Обеспечить шифрование данных при хранении и передаче.
- Настроить разграничение доступа через Keycloak (RBAC), чтобы доменные команды видели только свои данные.
- Вести аудит-логи всех операций с чувствительными данными.

**Управленческие меры:**
- Привлечь специалистов по compliance на этапе проектирования миграции, а не после.
- Провести классификацию и тэгирование данных до начала миграции: что относится к персональным данным, что к банковской тайне, что к медицинской тайне.

### Технологические риски

#### 8. Сложность одновременного внедрения большого числа технологий

**Технические меры:**
- Начать с пилотного домена и минимально необходимого набора технологий. Отработать на нём полный цикл (от сервиса до витрины), прежде чем подключать следующие домены.

**Управленческие меры:**
- Определить, какие технологии критичны на первом этапе (например, Kafka и Flink, Iceberg), а какие можно добавить позже (например, DataHub).
- Не пытаться внедрить весь стек одновременно — это главный принцип снижения этого риска.

#### 9. Миграция сотен терабайт из SQL Server 2008

**Технические меры:**
- Применить паттерн Strangler Fig (фикус-душитель) к данным: для пилотного домена развернуть Lakehouse и настроить репликацию новых данных из DWH. Параллельно перенести исторические данные. Когда и текущие, и исторические данные ,будут в Lakehouse, переключить потребителей и отключить эту часть DWH. Повторить для следующего домена.
- Перед переключением какое-то время сверять результаты запросов в старой и новой системах, чтобы убедиться в корректности.
- Продумать точку разреза между исторической миграцией и потоком новых данных, чтобы избежать дубликатов.

**Управленческие меры:**
- Выделить отдельную команду миграции с чёткими критериями приёмки для каждого домена.
- Мониторить нагрузку на DWH во время выгрузок, при необходимости выполнять их в непиковое время.

#### 10. Обеспечение exactly-once семантики для финансовых данных

**Техническое решение:**
- Использовать паттерн Transactional Outbox + Debezium для гарантированной доставки событий из доменных сервисов в Kafka.
- Настроить idempotent producers в Kafka и exactly-once обработку в Flink.
- На стороне ClickHouse использовать ReplacingMergeTree для дедупликации.
- Провести комплексное end-to-end тестирование на финансовых сценариях: имитация сбоев на каждом звене цепочки с проверкой, что данные не теряются и не дублируются.
